## 1. 절차적 맵 — 엔진 도형에서 실제 애셋으로 (7/21~7/27)

Necropolis(디아블로풍 폐허/묘지 마켓플레이스 팩)를 실제 바닥/장애물로 붙였다.
`Content/Necropolis/*`는 2.2GB라 gitignore.

### 1-1. 생성자에서 메시를 박아두던 코드를 걷어냄

```cpp
// 삭제된 코드 (AInfiniteMapGenerator 생성자)
static ConstructorHelpers::FObjectFinder<UStaticMesh> CubeFinder(TEXT("/Engine/BasicShapes/Cube.Cube"));
if (CubeFinder.Succeeded())
{
    FloorMesh = CubeFinder.Object;
    ObstacleMeshes.Add(CubeFinder.Object);
}
// Cylinder, Cone도 마찬가지로 삭제
```

프로토타입 시절엔 "빌드하면 바로 뭔가 보인다"가 이득이었는데,
이제는 BP에서 지정한 Necropolis 메시를 생성자가 매번 덮어써서 방해만 됐다.
**기본값 자동 지정은 애셋이 없을 때만 이득이다.** 애셋이 생기면 걷어내는 게 맞다.

### 1-2. 장애물 공중부양 — 피벗 전제가 바뀌었다

Necropolis 나무를 `ObstacleMeshes`에 넣었더니 전부 공중에 떴다.

```cpp
// 중심 피벗 메시를 바닥 위에 앉히기 위한 Z 오프셋
//const float HalfHeight = (ObstacleMeshBaseSize * Scale) * 0.5f;
const FVector Loc = Origin + FVector(LocalX, LocalY, 0);
```

원인은 코드가 아니라 **전제**였다. 엔진 기본 큐브는 피벗이 메시 정중앙이라 반높이만큼 띄워야 바닥에 앉는데,
건축/식생 프롭은 관례상 피벗이 밑동(발밑)에 있다. 같은 코드가 메시가 바뀌자 정확히 반대로 동작한 것.

> **삽질 기록**: "코드가 틀렸나"부터 봤는데 코드는 처음부터 맞았다.
> 틀린 건 `ObstacleMeshBaseSize`라는 변수가 **모든 메시에 같은 전제를 강요한다**는 설계 쪽이었다.
> 지금은 "피벗은 밑동"으로 통일했고, 중심 피벗 메시를 다시 쓰려면 메시별 오프셋이 필요해진다.

### 1-3. GenerateChunk 쪼개기

한 함수가 바닥·POI·디버그·장애물·마을을 전부 하고 있어서 세 개를 뽑아냈다.

```cpp
void SpawnObstacles(FRandomStream& Stream, FMapChunk& Chunk, FVector Origin, bool bIsPOIChunk);
void SpawnVillageGuards(const FVector& Center, FMapChunk& Chunk);
void SpawnVillagers(const FVector& Center, FMapChunk& Chunk);
```

동작은 그대로다. 뽑아내면서 알게 된 건 **경비병/주민/구조물이 전부 같은 모양의 코드**라는 것 —
`클래스 있나 확인 → 고정 슬롯 배열 → SpawnParams → 루프 → Chunk.SpawnedActors.Add`.
다음에 하나 더 늘어나면 그땐 진짜 공통 함수로 묶을 차례다(지금은 아직 셋뿐이라 참는다).

### 1-4. 마을 외곽 구조물 — 랜덤이 아니라 고정 슬롯

마을에 "집"이 필요해서 외곽 링(반경 2400)에 6개를 놓았다.

```cpp
static const FStructureSlot Slots[6] = {
    { FVector2D(1697.f,  1697.f), 225.f },
    { FVector2D(2400.f,     0.f), 180.f },
    { FVector2D(1697.f, -1697.f), 135.f },
    { FVector2D(-1697.f,-1697.f),  45.f },
    { FVector2D(-2400.f,    0.f),   0.f },
    { FVector2D(-1697.f, 1697.f), 315.f },
};
```

**좌표는 고정, 흔드는 건 메시 선택과 스케일(0.9~1.1)뿐이다.** 경비병/주민과 같은 원칙 —
위치까지 랜덤으로 뿌리면 발판이나 서로와 겹치는 걸 검사해야 하는데, 고정 슬롯이면 검사 자체가 필요 없다.
북(0°)/남(180°) 두 자리를 비워서 마을 안팎으로 길이 뚫린 것처럼 보이게 했다.

마을 중심 발판도 무기강화 발판 → **동료 소환존(랜덤 직업)** 으로 바꿨다. 마을에 들르는 이유가 더 직접적이다.

## 2. 직업 스탯 — FJobStats (7/29)

직업마다 다른 값(체력/공격력/이동속도/공속)을 `UJobComponent`가 소유하게 했다.

```cpp
USTRUCT(BlueprintType)
struct FJobStats
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Job|Stats")
    int32 MaxHP = 5;

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Job|Stats")
    int32 Damage = 1;

    /** 이동 속도(cm/s) — 캐릭터의 CharacterMovement->MaxWalkSpeed로 적용된다. */
    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Job|Stats")
    int32 Speed = 600;

    /** 자동 공격 간격(초). 0 이하면 캐릭터의 AttackInterval 폴백을 쓴다. */
    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Job|Stats")
    float AttackInterval = 0.4f;
};
```

> **삽질 기록**: 처음엔 멤버에 기본값을 안 줬더니 직업 BP Details에 전부 0으로 떴다.
> USTRUCT 멤버는 초기화 안 하면 쓰레기값이 아니라 0으로 채워지는데, 그 0이 그대로 BP에 저장돼버린다.
> `= 5`, `= 600` 같은 기본값은 "취향"이 아니라 **BP가 처음 보는 값**이라 반드시 필요하다.

### 설계값과 런타임 증가분을 분리

```cpp
// 추가 데미지 => 게임이 끝나면 사라져야 하는 값
UPROPERTY(Transient, BlueprintReadOnly, Category = "Job|Combat")
int32 BonusDamage = 0;

/** 실제 적용 피해량 = 직업 설계값 + 강화/버프 증가분. 공격 코드는 전부 이걸 쓴다. */
UFUNCTION(BlueprintPure, Category = "Job|Stats")
int32 GetDamage() const { return Stats.Damage + BonusDamage; }
```

강화 발판이 `Stats.Damage`를 직접 올리면 **직업 설계값 자체가 오염**돼서 판이 끝나도 안 돌아온다.
`Transient`를 붙여 "저장되면 안 되는 값"이라고 못 박고, 공격 코드는 전부 `GetDamage()`만 쓰게 했다.

### 스탯이 캐릭터로 흘러가는 지점

```cpp
void UJobComponent::InitializeForOwner(ACombatCharacter* Owner)
{
    OwnerCharacter = Owner;
    if (!OwnerCharacter) return;

    //값 전송
    OwnerCharacter->MaxHP = Stats.MaxHP;
    OwnerCharacter->SetHP(Stats.MaxHP);
    OwnerCharacter->Damage = Stats.Damage;

    if (UCharacterMovementComponent* Move = OwnerCharacter->GetCharacterMovement())
    {
        Move->MaxWalkSpeed = Stats.Speed;
    }
    //OwnerCharacter->AttackInterval = Stats.AttackInterval; => 어차피 계속 Get으로 받을 예정

    EquipWeapon();
}
```

`AttackInterval`만 전송하지 않는 이유가 재밌다. HP/속도는 **복사해야 하는 값**(전투 중 깎이고 변한다),
공속은 **매번 물어봐야 하는 값**이다. 그래서 3단 폴백 함수로 뺐다.

```cpp
float ACombatCharacter::GetAttackInterval() const
{
    if (CurrentJob && CurrentJob->Stats.AttackInterval > 0.0f)
        return CurrentJob->Stats.AttackInterval;
    return AttackInterval > 0.0f ? AttackInterval : 0.4f;
}
```

마지막 `0.4f`가 중요하다. **간격 0 = 매 프레임 공격**이라 폴백이 없으면 설정 실수 한 번에 초당 60타가 나간다.

### 전투 공통 로직도 같이 베이스로

`CreateJobComponent()` / `TickAttack()` / `HandleAttackNotify()`를 `ACombatCharacter`로 올렸다.
플레이어와 동료가 똑같은 코드를 각자 갖고 있던 걸 합친 것.

```cpp
bool ACombatCharacter::TickAttack(float DeltaTime, bool bWantsToAttack)
{
    TimeSinceLastAttack += DeltaTime;

    if (!bWantsToAttack || !CurrentJob || IsDead) return false;
    if (TimeSinceLastAttack < GetAttackInterval()) return false;

    TimeSinceLastAttack = 0.0f;
    CurrentJob->Attack();
    return true;
}
```

역할 분담이 깔끔해졌다 — **"언제 칠지"는 서브클래스**(플레이어=조준 입력, 동료=사거리 안 타겟),
**"어떻게 칠지"는 직업**, **쿨타임 관리는 베이스**.

## 3. UPROPERTY 하나 빠뜨려서 난 크래시 (7/29)

`UMyCanvas::UpdateCoinText`에서 EXCEPTION_ACCESS_VIOLATION. 원인은 이거였다.

```cpp
// 전
UMyCanvas* CanvasWidget;
APlayerController* controller;
AActor* playerStart;

// 후
UPROPERTY()
UMyCanvas* CanvasWidget = nullptr;
```

**UPROPERTY는 에디터 노출용이 아니라 GC 추적용이다.** 안 붙이면 GC가 "아무도 안 쓰네" 하고 회수해버리는데,
포인터 변수는 여전히 옛 주소를 들고 있다. 그래서 `if (CanvasWidget)` 검사를 **통과한 뒤에** 죽는다 —
null 체크를 다 해놨는데도 크래시가 나서 한참 헤맸다.

덤으로 `controller`는 이름도 바꿔야 했다.

```cpp
// 이름을 controller로 두면 안 된다 — APawn에 이미 Controller가 있고,
// UHT는 프로퍼티 이름을 FName(대소문자 구분 안 함)으로 비교해 shadowing 에러를 낸다.
UPROPERTY()
APlayerController* PlayerControllerRef = nullptr;
```

UPROPERTY를 붙이는 순간 UHT의 이름 검사 대상이 되면서, 그동안 조용했던 `Controller` 섀도잉이 컴파일 에러로 튀어나왔다.

HP바 폭도 같이 고쳤다: `HP * 100` → `HP * 500 / MaxHP`. 직업마다 MaxHP가 달라졌으니 절대값은 못 쓴다.

## 4. 헤더 대청소 (7/31~8/1)

`MyPlayer.h` 400줄 이상을 재배치했다. 규칙을 정하고 주석으로 박아뒀다.

```cpp
/*
    여담으로 get set같은 프로퍼티와 부품 함수라면 밑 public에 넣어라.
    1. 핵심 메인 함수
    2. 핵심 메인 변수
    3. 부품 변수
    4. 부품 함수 => 프로퍼티
    private도 변수는 앞에
*/
```

멤버는 대부분 `private` + `meta = (AllowPrivateAccess = "true")`로 내렸다.
BP에서는 그대로 보이는데 C++에서는 아무 데서나 못 만진다 — **BP 편의를 포기하지 않고 캡슐화만 얻는 조합**이다.

`AttackMontage` → `DefaultAttackMontage`로 개명. 이름이 "이게 기본 폴백"이라는 걸 말해주게.

> **주의로 배운 것**: 파라미터 이름은 함부로 못 바꾼다.
> BP는 핀을 C++ 파라미터 이름(FName)으로 저장해서, `add_hp`를 `Amount`로 바꾸면 기존 BP 연결이 "핀 못 찾음"으로 깨진다.
> 변수명 리네임도 같은 이유로 BP에 지정해둔 값이 조용히 None이 된다.

## 5. 무기 슬롯 — 양손 (8/1~8/2)

### 5-1. 슬롯 찾기를 베이스로 → 동료도 무기를 든다

무기 ChildActor를 찾아 캐시하는 코드가 `AMyPlayer`에만 있었다. `ACombatCharacter::InitWeaponSlot()`으로 올리니
**동료가 공짜로 무기를 들게 됐다.** `SetWeaponMesh` → `EquipWeapon`으로 개명.
무기 메시 애셋도 `Content/Mesh/Weapon/` 아래로 통합(Grail, Stape 이동 + bow, SK_CrossBow 추가).

### 5-2. 슬롯을 C++이 소유

```cpp
// 무기 슬롯은 양손 고정 2개. C++이 소유하므로 BP에서 추가할 필요가 없고,
// BP가 부모 참조를 잃어도 슬롯이 사라지지 않는다.
WeaponRight = CreateDefaultSubobject<UChildActorComponent>(TEXT("WeaponRight"));
WeaponRight->SetupAttachment(GetMesh(), RightHandSocket);

WeaponLeft = CreateDefaultSubobject<UChildActorComponent>(TEXT("WeaponLeft"));
WeaponLeft->SetupAttachment(GetMesh(), LeftHandSocket);
```

전에는 BP에 붙인 ChildActorComponent를 **태그(`Weapon`)로 찾아 쓰는 방식**이었다.
BP가 부모 클래스 참조를 잃는 사고를 몇 번 겪고 나니, 구조에 필수인 컴포넌트를 BP에 맡기면 안 되겠다 싶었다.

### 5-3. 손은 직업이 정한다

```cpp
/** 무기를 드는 손. 직업이 이 값을 들고 있고, 캐릭터는 이 값만 보고 슬롯을 고른다.
 *  → 캐릭터 코드가 직업 종류(EJobType)를 알 필요가 없다. 직업이 늘어도 분기는 손 개수(2)로 고정. */
UENUM(BlueprintType)
enum class EWeaponHand : uint8
{
    Right UMETA(DisplayName = "오른손"),
    Left  UMETA(DisplayName = "왼손"),
};
```

활은 왼손으로 들고 오른손으로 시위를 당기니 궁수만 `Left`다.
여기서 `if (JobType == Archer)`로 갔으면 직업이 늘어날 때마다 캐릭터 코드가 같이 늘어난다.
**직업이 자기 정보를 들고 오게 하면 캐릭터의 분기는 손 개수 2로 영원히 고정된다.**

```cpp
// 반대 손은 반드시 숨긴다.
// 이걸 빼먹으면 직업을 바꿨을 때 이전 직업 무기가 반대 손에 그대로 남는다(왼손 활 + 오른손 검).
if (OtherMesh)
{
    OtherMesh->SetVisibility(false);
}
```

### 5-4. 부착 규칙 하나로 각도가 날아간다

```cpp
// KeepRelativeTransform: 슬롯 컴포넌트에 설정해둔 Relative Location/Rotation을 유지한 채 붙인다.
// (SnapToTarget을 쓰면 상대 트랜스폼이 리셋돼서 BP에서 맞춘 각도가 통째로 날아간다)
Slot->AttachToComponent(MeshComp, FAttachmentTransformRules::KeepRelativeTransform, SocketName);
```

무기 잡는 각도는 **소켓이 아니라 슬롯 컴포넌트의 Relative Rotation**으로 맞추기로 정했다.
소켓은 스켈레톤(= 모든 캐릭터 공용)에 붙지만 각도는 무기마다 다르니까.

### 5-5. 실패를 조용히 넘기지 않기

없는 소켓에 붙이면 언리얼은 에러 없이 **캐릭터 원점(발밑)** 에 붙여버린다. 이게 제일 고약해서 전용 로그 카테고리를 팠다.

```cpp
/** 무기 슬롯 전용 로그 카테고리.
 *  출력 로그 창 → Categories 드롭다운에서 'LogWeapon'만 체크하면 무기 관련 로그만 볼 수 있다.
 *  (LogTemp에 섞어 쓰면 다른 노란 경고에 묻힌다) */
DECLARE_LOG_CATEGORY_EXTERN(LogWeapon, Log, All);
```

실패 지점(슬롯 없음 / 소켓 없음 / 액터 스폰 실패 / SkeletalMesh 없음)마다
**무엇이 잘못됐고 어디를 고쳐야 하는지**까지 로그 + 화면 메시지(빨강)로 남겼다.

한 가지 구분이 중요했다 — `WeaponActorClass`가 비어 있는 건 **에러가 아니라 선언**이다.

```cpp
// WeaponActorClass를 비워둔 건 "이 캐릭터는 무기 슬롯을 안 쓴다"는 선언이다(적 등).
// 잘못된 설정이 아니므로 소켓 검사도, 경고도 하지 않고 조용히 빠진다.
if (!WeaponActorClass)
{
    UE_LOG(LogWeapon, Verbose, TEXT("[%s] 무기 슬롯 미사용(WeaponActorClass 없음)."), *GetName());
    return;
}
```

좀비가 나올 때마다 빨간 경고가 뜨면 로그는 그날로 쓸모없어진다.

## 6. 궁수 활 시위 애니메이션 (8/2)

활을 쐈는데 시위는 가만히 있으니 어색했다. 두 가지를 고쳤다.

### 6-1. 발사 시점을 Notify → 몽타주 종료로

```cpp
// 공격 몽타주가 끝나는 순간 = 활시위를 놓는 순간(애니 마지막 프레임)인 직업용.
// 전사처럼 중간에 타격하는 직업은 Notify를 쓰므로 여기 반응하지 않는다.
void ACombatCharacter::OnAttackMontageEnded(UAnimMontage* Montage, bool bInterrupted)
{
    if (bInterrupted)
    {
        return; // 취소된 공격은 발사하지 않는다
    }
    if (CurrentJob)
    {
        CurrentJob->OnAttackMontageEnded();
    }
}
```

`bInterrupted` 체크가 핵심이다. 안 그러면 맞아서 공격이 끊겨도 화살은 나간다.

### 6-2. 시위 배속을 역산

시위 애니를 그냥 재생하면 몽타주보다 먼저 끝나거나 늦게 끝난다. 그래서 **남은 시간에서 배속을 계산**했다.

```cpp
// 활 시위가 몽타주 끝(=활 놓는 순간)에 딱 맞춰 다 당겨지도록 배속을 계산한다.
// Notify 위치를 옮기거나 공속이 바뀌어도 자동으로 따라온다.
const float Pos = Anim->Montage_GetPosition(Montage);
const float MonRate = FMath::Max(Anim->Montage_GetPlayRate(Montage), KINDA_SMALL_NUMBER);
const float Remaining = (Montage->GetPlayLength() - Pos) / MonRate;

if (Remaining > KINDA_SMALL_NUMBER)
{
    Rate = BowDrawAnim->GetPlayLength() / Remaining;
}
Single->SetPlayRate(Rate * BowDrawRateScale);
```

숫자를 손으로 맞췄으면 `AttackInterval`을 바꿀 때마다 다시 맞춰야 했을 것이다.
**공속이 스탯이 된 이상, 연출도 스탯을 따라가야 한다.** `BowDrawRateScale = 1.05`는 살짝 먼저 당겨지게 하는 미세조정용.

## 7. 안정화 (8/3)

### 7-1. 에디터 시작 크래시 — 생성자에서 BP를 부르면 안 된다

`InfiniteMapGenerator.cpp:53`에서 ACCESS_VIOLATION으로 에디터가 아예 안 열렸다.

```cpp
// 삭제한 코드
static ConstructorHelpers::FClassFinder<AActor> VillagePadFinder(TEXT("/Game/BP/GameObject/BP_CompanionSpawnZone"));
static ConstructorHelpers::FClassFinder<ACompanion> VillageGuardFinder(TEXT("/Game/Characters/Companion/BP_Companion"));
```

C++ 클래스의 CDO는 **BP보다 먼저 만들어진다.** 그 시점에 BP 클래스를 끌어오면 아직 준비 안 된 걸 건드리게 된다.
`/Engine/BasicShapes/Cube` 같은 엔진 애셋은 항상 있으니 괜찮았지만, `/Game/...` BP는 다르다.

> **규칙으로 정리**: 생성자에서 `FObjectFinder`로 엔진 애셋은 OK, `FClassFinder`로 게임 BP는 금지.
> 기본값은 BP Details에서 지정한다 → 그래서 `EditAnywhere, BlueprintReadOnly`를 `BlueprintReadWrite`로 완화했다.

### 7-2. 적이 추격만 하고 공격을 안 함 / 사망 애니 미재생

둘 다 진짜 수정은 **`ABP_Enemy`(에디터 작업)** 였다. C++ 쪽에서 같이 한 건 델리게이트 중복 방어뿐.

```cpp
PFC->OnRequestFinished.RemoveAll(this);   // ← 추가: 이미 걸려 있으면 제거 후 재등록
PFC->OnRequestFinished.AddUObject(this, &AEnemy::MoveCompleted);
```

적은 풀에서 재사용되니 AI 컨트롤러 세팅이 여러 번 돈다. 그때마다 `AddUObject`만 하면
**바인딩이 쌓여서 이동 완료 한 번에 콜백이 여러 번** 불린다.

곁다리로 메뉴 위젯도 고쳤다.

```cpp
MenuWidget->SetIsFocusable(true);   // ← AddToViewport 전에 호출해야 먹는다
MenuWidget->AddToViewport();
```

## 8. UCombatRegistrySubsystem (8/3~8/4)

적이 타겟을 고르는 코드가 이랬다.

```cpp
// 전 — AEnemy::TrackingPlayer
AMyPlayer* myPlayer = Cast<AMyPlayer>(UGameplayStatics::GetPlayerCharacter(GetWorld(), 0));
if (!myPlayer || IsDead) return;
// 플레이어 거리 재고...
for (ACompanion* companion : myPlayer->GetCompanions()) { /* 동료 거리 재고... */ }
```

**적이 플레이어를 알아야 하고, 플레이어의 동료 목록까지 알아야 한다.**
마을 주민이나 경비병은 플레이어 목록에 없으니 영원히 타겟이 안 된다.

### 팀 + 레지스트리

```cpp
UENUM(BlueprintType)
enum class ETeam : uint8
{
    Ally     UMETA(DisplayName = "아군"),   // 플레이어, 동료
    Enemy    UMETA(DisplayName = "적"),
    Neutral  UMETA(DisplayName = "중립"),
};
```

`ACombatCharacter`가 BeginPlay/EndPlay에서 스스로 등록/해제한다.

```cpp
void ACombatCharacter::BeginPlay()
{
    Super::BeginPlay();
    if (UCombatRegistrySubsystem* Reg = GetWorld()->GetSubsystem<UCombatRegistrySubsystem>())
    {
        Reg->Register(this);
    }
    ...
}
```

```cpp
/** TWeakObjectPtr인 이유: 액터가 파괴돼도 이 배열이 그걸 살려두지 않는다.
 *  UPROPERTY()로 강참조하면 죽은 적이 GC되지 않고 계속 남는다. */
TArray<TWeakObjectPtr<ACombatCharacter>> Characters;
```

`AddUnique`(중복 방어) / `RemoveSingleSwap`(순서가 필요 없으니 마지막 원소로 덮기 — O(n) 밀어내기보다 빠름)을 썼다.

### 질의 한 줄

```cpp
ACombatCharacter* target = Reg->FindNearestOfEnemy(myLocation, ETeam::Ally, 2500);
```

내부에서 신경 쓴 것 세 가지:

```cpp
// IsValid  : 파괴됐거나 GC 대기 중
// IsHidden : 풀에서 대기 중인 적 (EnterPoolDormancy로 숨겨진 상태)
// GetIsDead: 죽었지만 아직 시체가 남아있는 상태
if (!IsValid(Candidate) || Candidate->IsHidden() || Candidate->GetIsDead()) continue;
```

- **제곱 거리 비교** — `sqrt`를 한 번도 안 부른다. `MaxDistance <= 0`이면 제한 없음.
- **2D 거리** — 평면 게임이라 Z를 넣으면 언덕 위 적이 부당하게 멀어진다.
- `DoesSupportWorldType`으로 Game/PIE에서만 생성 (에디터 프리뷰 월드에서 안 돌게).

이제 적은 플레이어도, 동료 목록도 모른다. **"가장 가까운 아군"만 물어본다.**
주민/경비병에게 `TeamType`만 지정하면 자동으로 타겟 후보가 된다.

## 9. 하드코딩 걷어내기 (8/4)

```cpp
// 전
#define MAX_ENEMY_SIZE 20
#define MAX_COIN_SIZE 10

// 후
UPROPERTY(EditDefaultsOnly, BlueprintReadWrite, meta=(AllowPrivateAccess = "True"), Category = "Pool")
int Max_Enemy_Size = 20;
```

`#define`은 전처리기라 BP에서 볼 수도, 빌드 없이 바꿀 수도 없다. 밸런스 숫자가 전처리기에 있을 이유가 없다.

`AttackRange`도 정리했다. `AEnemy::attackRange`(100, private 하드코딩)와 `ACompanion::AttackRange`(160)로
같은 개념이 두 군데 있었는데, **베이스 `ACombatCharacter`로 승격**하고 둘 다 지웠다.

가장 중요한 건 이거였다.

```cpp
void AEnemy::BeginPlay()
{
    Super::BeginPlay();
-   SetHP(5);
    CanAttack = true;
-   Damage = 1;
```

```cpp
- enemy->SetHP(5);              // 죽었던 적이면 부활 전환(OnRevive)까지 발동
+ enemy->SetHP(enemy->GetMaxHP());
```

BP에서 적 체력을 아무리 올려도 BeginPlay와 스폰 코드가 5로 덮어써서 안 먹었다.
**"값을 BP로 옮겼다"는 건 C++에서 그 값을 쓰는 자리를 전부 지웠다는 뜻이어야 한다.** 하나라도 남으면 옮긴 게 아니다.
