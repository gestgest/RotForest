# 개발로그 — 좌클릭 공격 조준

로스트아크식 조작(우클릭 이동 / 좌클릭 공격)에서 공격이 커서 쪽으로 나가게 만드는 작업.
2026-09-19 증상 발견 ~ 진행 중.

---

## 1. 증상

좌클릭하면 공격은 나가는데 **방향이 커서가 아니라 이동 방향**이었다.

재현 조건이 묘했다.

| 조작 | 결과 |
|---|---|
| 좌클릭 꾹 누르고 있기 | 정상 — 커서 쪽으로 나감 |
| 좌클릭 짧게 탭 | 버그 — 이동 방향으로 나감 |

이 차이가 원인을 그대로 가리키고 있었다.

## 2. 원인 — 방향을 "발사 시점"에 읽고 있었다

공격은 두 시점으로 쪼개져 있다.

```
클릭 프레임  ──────── 0.2~0.4초 ────────>  몽타주 Notify (실제 타격/발사)
```

발사체 스폰 코드(`JobComponent::SpawnProjectileForward`, `WarriorJob`)는 두 번째 시점에 호출되는데,
거기서 `GetActorForwardVector()`를 **그 자리에서** 읽고 있었다.

그 사이에 액터 yaw는 누가 바꾸느냐 — 매 Tick `AMyPlayer::UpdateAimAndAttack`이 다시 쓴다.

```
Face = bAiming ? Aim : Move      // bAiming = 좌클릭 중인가
```

탭으로 클릭하면 버튼을 뗀 **다음 프레임부터** `bAiming = false`가 되고, 몸이 `RInterpTo`로
이동 방향을 향해 돌아가기 시작한다. Notify는 그 뒤에 터진다.
→ 클릭할 땐 커서를 봤는데, 정작 때리는 순간엔 이동 방향을 보고 있었다.
꾹 누르고 있으면 `bAiming`이 계속 true라 증상이 안 보였던 것.

## 3. 1차 수정 — 방향 래치(latch)

`ACombatCharacter`에 `AttackAimDir`를 두고, `TickAttack`에서 `CurrentJob->Attack()` **직전에** 고정했다.
발사체/스윕은 `GetActorForwardVector()` 대신 `GetAttackAimDir()`를 쓴다.

여기에 `AMyPlayer::AttackFacingHold`를 같이 넣었다.
판정만 고치면 캐릭터가 딴 데 보면서 화살을 옆으로 쏘는 그림이 되므로,
몽타주 길이만큼은 몸이 이동 방향으로 되돌아가지 않게 막는 장치.

`TickAttack`이 불리는 시점에 액터가 이미 커서를 보고 있는 건 Tick 순서가 보장한다.

```
MouseInput  ->  UpdateMovement  ->  UpdateAimAndAttack
                                      ├ bAiming이면 SetActorRotation 스냅
                                      └ TickAttack  <- 여기서 정면을 읽음
```

**결과: 제자리에서 탭 클릭은 정확히 커서로 나간다.** 회귀 없음.

## 4. 그런데 아직 빗나간다 — 옆으로 달리면서 쏠 때

래치는 "언제 읽느냐"를 고쳤을 뿐, **무엇을 저장하느냐**는 그대로 방향이다.
방향은 내 위치를 원점으로 한 상대값이라, 원점이 움직이면 같이 끌려간다.

```
클릭 순간:  플레이어(0,0)  커서(1000,0)     -> 저장된 방향 (1,0)
0.3초 뒤:   플레이어(0,300)으로 이동, Notify 발사
            (1,0)으로 발사  ->  (1000,300) 쪽으로 날아감. 적과 평행하게 빗나감
```

좌표 `(1000,0)`를 저장해뒀다면 발사 프레임에 `목표점 - 현재위치`로 다시 빼서
그때의 올바른 방향이 저절로 나온다. 내가 얼마나 움직였든 상관없이.

→ **다음 작업: 래치하는 값을 방향에서 좌표로 바꾼다.**

## 5. 구현 전에 알아야 할 배경

"좌표를 저장하면 된다"는 한 줄인데 구현은 한 줄이 아니다. 걸리는 게 네 개 있다.

### (1) 기존 입력 파이프라인에 좌표를 못 태운다

`MouseInput`은 세 덩어리다.

```
(A) 커서 -> 월드 좌표      : GetCursorGroundLocation(Cursor)
(B) 좌표 -> 쓸 만한 방향   : ToCursor, StopRadius 컷, Normalize, LastCursorDir 폴백
(C) 결과 배분              : bRight -> MouseMove / bLeft -> MouseAim
```

문제는 `MouseAim`의 자료형이 **`FVector2D`**라는 것. 게임패드 스틱 포맷에 맞춰 정규화되면서
**거리 정보가 버려진다.** 방향만 남는다.

즉 좌표는 이 관을 통과할 수가 없다. 멤버 캐시 + setter라는 **별도 경로**를 새로 파야 한다.
이게 이 작업이 한 줄로 안 끝나는 이유의 전부다.

| 경로 | 값 | 용도 |
|---|---|---|
| `MouseAim` (기존) | 방향 | 클릭하는 동안 몸이 커서를 바라보게 |
| 새 경로 | 좌표 | 발사 시점에 방향을 재계산 |

둘 다 필요하다. 하나로 못 합친다.

또 커서는 화면에 하나뿐이라 (A)는 이동/조준 공통이고, `CursorStopRadius` 컷은
"커서가 가까우면 캐릭터가 진자운동하는" 이동 전용 사정이다.
→ 좌/우클릭 분리선은 **(A) 뒤, (B) 앞**에 그어야 한다.

### (2) 값을 어느 클래스가 소유하나

`AMyPlayer`가 아니라 `ACombatCharacter`다. 이유는 **`ACompanion::Tick`도 `TickAttack`을 부르기 때문.**
플레이어에만 넣으면 컴파일은 되는데 동료 공격이 조용히 깨진다.

> 멤버를 어느 계층에 둘지는 "누가 그 함수를 부르는가"가 정한다.

### (3) 실행 순서가 코드 위치를 강제한다

좌표를 밀어넣는 setter 호출은 `TickAttack`보다 **먼저** 실행돼야 한다.
3번의 Tick 순서도 그대로 제약이 된다 — `MouseInput` 단계에서 캐시하면 자연히 만족된다.

### (4) 읽는 쪽이 3군데고, 그중엔 커서가 없는 놈들이 있다

`JobComponent.cpp:110`, `WarriorJob.cpp:35`, `WarriorJob.cpp:59`.
동료와 적도 이 코드를 탄다. **걔들한텐 마우스 커서가 없다.**

→ `GetAttackAimDir()`는 단순 게터가 아니라 폴백 사다리가 돼야 한다.

| 순위 | 값 | 걸리는 상황 |
|---|---|---|
| 1 | 좌표에서 재계산한 방향 | 플레이어 |
| 2 | `AttackAimDir` (기존 방향 래치) | 동료·적, 발밑 클릭 |
| 3 | `GetActorForwardVector()` | 한 번도 공격한 적 없음 |

`AttackAimDir`를 지우면 안 되는 이유가 이거다. 2순위 폴백 자리로 계속 산다.

## 6. 함정 메모

- **`FVector` 기본값 `(0,0,0)`은 월드 원점이다.** "값 없음"과 구분이 안 되므로 bool 플래그가 따로 필요하다.
- **`GetSafeNormal()`은 너무 짧으면 0벡터를 반환.** 그대로 `Rotation()`에 넣으면 yaw=0 → 월드 +X축으로 쏜다. 발밑 클릭이 이 케이스.
- **Z 성분.** 커서 평면은 플레이어 Z 기준이라 높이 차가 있으면 위아래로 쏜다. `To.Z = 0` 필수.
- **축 스왑.** 월드(X=앞, Y=오른쪽) → 스틱(X=오른쪽, Y=위)이라 `FVector2D(Dir.Y, Dir.X)`. 조준 경로에서도 빼먹지 말 것.
- **`ToCursor` 재사용 금지.** `&&`가 단락 평가라 `Normalize()`가 실행된 경우와 아닌 경우로 상태가 갈린다.

| 상황 | SizeSquared 검사 | Normalize 실행 | 그 시점 `ToCursor` |
|---|---|---|---|
| 커서가 멀다 | 통과 | O | 길이 1 |
| 커서가 가깝다 | 실패 | X | 원래 짧은 길이 |

## 7. 알려진 한계 (이번 작업 범위 밖)

우클릭+좌클릭을 동시에 누르면 커서가 하나뿐이라 **이동 방향 = 공격 방향**이 된다.
"달리면서 반대쪽 공격"은 구조적으로 불가능하다.
원한다면 우클릭을 목적지 지정형으로 바꾸거나, 좌클릭 중에는 이동 방향을 직전 값으로 고정해야 한다.
독립된 설계 결정이라 나중에 정해도 된다.

참고로 상하체 분리는 이미 있다 — `UpdateLegYawOffset` + AnimBP의 pelvis(+)/spine_01(-).
액터 yaw가 공격 방향으로 유지되면 다리는 자동으로 속도 방향을 향한다. 새로 만들 필요 없음.

---

## 8. 테스트 체크리스트

1. 제자리 탭 클릭 → 커서로 나가나 (회귀 확인)
2. **옆으로 달리면서 탭 클릭 → 클릭 지점으로 수렴하나** (이번 작업의 핵심)
3. 발 근처(StopRadius 안) 클릭 → 공격이 씹히지 않나
4. 적을 향해 달리며 근접 공격 → 몸이 이상하게 돌지 않나
5. 발밑을 정확히 클릭 → +X축으로 안 쏘나 (0벡터 폴백)
6. 동료가 적을 제대로 때리나 (회귀)
